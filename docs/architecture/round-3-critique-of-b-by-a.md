The other design has a useful separation between transport adapters and replay responders, and its loopback-only container arrangement is more concrete than a list of network prohibitions. Its central guarantees nevertheless exceed its mechanisms: holding a message’s final bytes does not make streaming observations durable, replaying recorded model outputs does not restore arbitrary harness state, and matching write histories does not establish that a response remains valid.

1. **The capture guarantee fails before a message finishes.** Sections 3.2 and 5 release all but the last frame before recording succeeds, then release even that frame when the queue or recorder fails. A harness can act on an SSE event or CLI output before the entire response ends. [SSE dispatches individual events during the stream](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation), so withholding the HTTP body’s last bytes does not protect already observed events. If `last` instead means each SSE event or CLI fragment, the architecture must say so; it then requires per-observation recording rather than its advertised one write per message. A bounded queue also bounds memory, not the time a filesystem write can stall. The design explicitly accepts power-loss loss and cannot claim “every delivered whole message is in its segment” when its failure rule releases unrecorded messages. This conflicts with the task’s fail-safe goal and SPEC §§1–3’s retrospective capture premise.

2. **Its storage rules contradict each other.** Section 3.2 promises no flush on the call path, but §3.3 flushes a blob before appending its referring event, and forwarding waits for that event. Large messages therefore do wait on a flush. A single append `write()` is not necessarily complete: [write(2)](https://man7.org/linux/man-pages/man2/write.2.html) permits short writes and delayed errors. Renaming a flushed blob does not durably publish its directory entry; [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html) requires a separate directory synchronization. These are correctness requirements for its chosen files, not reasons to introduce a database. Coverage written only at close also disappears precisely when capture crashes. A model-API record cannot universally repair the gap: the same storage can fail, and the harness might never send the result to the model.

3. **Universal mark replay is unproved, and its mark definition imports future evidence.** Section 3.4 puts an entire call before the mark when the call began before it—even if its response arrived afterward. That gives the reconstructed prefix information the agent did not yet possess. Timestamp sorting also cannot establish causal order across independent recorders. Section 3.6 then launches the edited harness from the beginning and promises the same state merely by imposing recorded exchanges. A tool that wrote a local file, a generated identifier retained in memory, or a changed initialization path breaks that promise. Claude’s documentation explicitly distinguishes conversation restoration from filesystem restoration: [SDK sessions persist the conversation, not the filesystem](https://code.claude.com/docs/en/agent-sdk/sessions). SPEC §3 requires a frozen prefix; calling an incomplete reconstruction universal does not satisfy it. Imposed-prefix replay is valuable for reconstructible harnesses, but it is not a general process-state restore.

4. **The recorded-answer rule assumes that “no writes” means “same answer.”** Section 3.5 repeats the last read indefinitely when write histories agree. A read can depend on virtual time, pagination state, authorization, background changes in the captured history, or nondeterministic ranking. [HTTP safety and idempotence concern requested effects, not identical response values](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2). An unchanged write history is useful evidence, not sufficient applicability. The generic default should consume recorded occurrences and reuse a response only under an explicit stability rule; otherwise it should proceed through SPEC §3’s answer chain. Marking an unjustified repetition `derived` discloses its origin but does not make the derivation valid.

5. **One state holder is stated but not maintained across resolver hits.** The overlay and emulator initialize at the mark, but the recorded resolver returns before them. The design does not specify how every recorded replay write updates the chosen state holder before a later miss reaches it. That can produce a recorded successful update followed by an emulator read of the old value. Prefix writes can also be applied twice if the imported Snapshot already contains their effects. State artifacts need an explicit frontier, and every accepted write needs a recorded transition, an explicit no-op, or an unknown-state effect. The core-owned entity-map language adds CRUD, filtering, invalidation, and completeness semantics despite SPEC §3’s small plugin boundary. Those semantics are better owned by connector plugins, where recurrence and permissions already belong.

6. **The privacy and model-history claims are too strong.** Whole-message redaction and incremental spooling after a finite look-behind window are not interchangeable; a later field can change whether earlier bytes are sensitive. `unscanned` media stored by default cannot meet SPEC §3’s promise that personal data is redacted when recorded. Also, not every model request contains the entire history: [OpenAI supports `previous_response_id` and persistent conversations](https://developers.openai.com/api/docs/guides/conversation-state), and [Anthropic supports server-maintained message threads](https://platform.claude.com/docs/en/build-with-claude/working-with-messages). Recording requests is necessary, but reconstructing the model’s actual context also requires captured referenced content or an honest limitation.

7. **The lock protects against accidental changes, not the Improver.** A checksum file beside an editable repository does not prevent an outside coding agent from modifying both the check and its checksum. The Workbench having no check-writing method does not help when that agent has unrestricted direct filesystem access. SPEC §2 says whoever tries to pass the check cannot edit it. Approval authority must be outside the Improver’s writable boundary, and results must bind to that authoritative approved digest. Portable lock files remain useful integrity records, but imported locks require acceptance rather than automatic trust.

8. **The verdict rules mishandle deterministic failures and already-passing baselines.** Section 3.8 makes only *clean* deterministic failures binding, while SPEC §3 says Phoenix’s deterministic results are binding. Its rules also leave the sample with a tainted failing expectation without a clear outcome: it neither meets “every expectation passes” nor necessarily has a clean failure. Synthesis should qualify the verdict’s confidence, not erase an observed prohibited call. Separately, a baseline can meet the majority threshold and still have fewer successful samples than the candidate. Declaring “nothing to pass” whenever the baseline meets the check contradicts the stated strict-improvement comparison. I agree that the spec permits explicitly discounted passes; forbidding them altogether is unnecessarily restrictive.

9. **Automatic recovery needs exclusive ownership, not merely files.** “Any process can pick up where another stopped” needs a claim protocol; otherwise two controllers can start the same unfinished sample. A plan hash is an input identity, not an operation identity: two intentional runs may share a plan. Conversely, a reconnect retry should not create another run. Reconstructing an interrupted attempt from its own trace is sound only when local state and emulator state are recoverable. Starting fresh after prefix drift does not restore the same execution and can select for attempts that happen to complete. SPEC §3’s Workbench and the task’s recovery goal require durable accepted operations, exclusive supervision, retained attempts, and explicit uncertainty.

10. **The sandbox mechanism is promising, but its VM and clock claims need correction.** Docker’s [`--network none`](https://docs.docker.com/engine/network/drivers/none/) supplies a concrete container boundary. The VM configuration, however, has a network device despite the claimed universal “no network device” contract. [QEMU `restrict=on`](https://www.qemu.org/docs/master/system/invocation.html) is a different valid mechanism, not the same topology. More importantly, setting guest time once and separately advancing an engine clock does not give the harness and emulators one clock, especially across prefix reconstruction and a mark transition. The clock needs one authority and a defined boundary transition.

11. **Two capture shortcuts change semantics.** Choosing a PTY solely because stdout is a terminal ignores stdin and stderr topology and can merge streams or change line discipline. Also, assigning underlying HTTP traffic to the only in-flight MCP call still guesses causality: background refreshes can overlap that call. SPEC §3 asks to preserve what the harness did. Terminal topology must be preserved or declared unsupported, and parent links require actual correlation rather than an occupancy heuristic.

12. **The harness and sharing rules impose unnecessary restrictions.** Requiring a git base excludes the spec’s broader “anything that can run a task and read its endpoints from config” contract. Ignoring every untracked file prevents the Improver from adding a permitted tool or prompt file. Meanwhile, a bundle that “contains no code” cannot by itself carry the custom TypeScript check that the same design locks and executes. Captured data should be separate from harness and tool implementations, as SPEC §2 requires; explicitly identified custom-check code can accompany a Moment without bundling either implementation.
