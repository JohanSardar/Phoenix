1. **Whether a disk flush belongs on the production call path, and whether Phoenix may stop the agent.** They commit every frame durably before delivering it and pause or fail forwarding when storage cannot commit. I hold only the last bytes of a message until its record is written, sync continuously off the call path, slow down when the recorder is behind, and keep the agent running if storage fails, with the hole visible from sequence numbers. My case: SPEC §3 says capture runs "in production, without changing what the agent does", and a recorder that halts an agent between two real-world writes changes what it does in the worst way. Their flush cannot buy what it costs, by their own admission that a vendor's side effect cannot be committed atomically with a local journal. And the cost is paid on every frame of every stream forever, on a flush Apple documents as one that "may take quite a while". The remaining exposure in my design is one unsynced batch at a power loss; the harness is dead at that moment too. This is a product call, so it is question 1 with the intermediate level spelled out.

2. **How a Replay starts from the mark.** They require a harness-specific continuation format and block the mode without one. I re-run the candidate from the start against recorded answers, with history frozen and configuration editable. My case: the spec promises replay from the mark and a three-item contract, and mine is the only mechanism that delivers both for a brand-new harness and the reference harness. Theirs asks the user to add a fourth contract item. Their exactness objection does not separate the designs: a candidate that imports a transcript also builds its state with candidate code, and their own crash recovery re-runs the candidate against recorded exchanges. Mine verifies every prefix request against the recording and stops on the first difference; an importer verifies nothing. Where a harness cannot re-run its prefix deterministically, echo shows it and the mode is unavailable for that harness, which is the same outcome theirs gives every harness without a session format.

3. **Discounted pass versus incomplete.** They make any required condition that rests on synthesized data incomplete. I evaluate everything, keep clean failures binding, and mark a result that rests on tainted evidence as discounted, never as a plain pass. My case: the spec's own words are "so a pass can be trusted or discounted" and "kept out of the pass/fail decision where possible". Under their rule the synthesized tier can never produce a verdict, so step 5 of the answer chain is dead weight for the loop. Their test for it, whether independence "can be established", cannot be decided once a synthesized answer is in a model's context.

4. **Where the trust boundary sits in a Replay.** They put the answer chain, plugins and frozen evidence in the worker with the candidate and enforce the network with a host policy that denies listed things. I put the engine, the recording, the trace and the check outside a sandbox that has no network device and one channel. My case: the candidate includes code the Improver edited, so anything it can read or write is not evidence. A sandbox that never holds the after-mark recordings or the trace cannot leak or alter them. And a deny-list has to be correct on Docker on Linux, Docker Desktop's VM and rootless Podman separately, while `--network none` and QEMU's `restrict=on` are documented to leave nothing to deny.

5. **A read the original made, asked once more.** They say an exhausted recording must fall through unless a connector rule allows reuse. I answer a repeat of an approved read-only call from the last current observation, labeled `derived`, unless a plugin marks the operation volatile or the manifest turns repeats off. My case: the spec says the Workbench answers "from the frozen copy" and that changes made live after the moment never affect a replay; in a frozen world with no writes since, the last observation is the answer. Without this, a fixed agent that double-checks the calendar on a connector with no plugin diverges, and that is the common case the spec says replay is strongest for. The label, the note and the fidelity report keep it honest.

6. **Who owns the overlay.** They make every overlay connector-owned code behind one state authority, with a durable transaction per write. I keep a small declarative entity map in the core for lookups by id and complete lists, send everything richer to an emulator, and rebuild state from the sample's own trace after a crash. My case: the spec's own overlay example is "a single-event lookup can be answered from an earlier list of events", which a map of paths answers with no connector code, so a connector gets step 2 of the chain by writing a descriptor. Recurrence, permissions and ranking are misses in the map by construction, not wrong answers. And a per-write durable journal inside a throwaway sandbox protects against a failure that also kills its only consumer.
