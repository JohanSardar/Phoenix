The other design is careful about honesty (provenance, incompleteness, unknown outcomes) and I take several points from it, listed at the end. Its main problems are that it trades the spec's Capture rule for a durability promise, leaves the hardest mechanisms unspecified, and reaches for heavier machinery than the spec needs.

**1. Capture that can pause production contradicts the spec.** Section 3.1 records "each response or stream segment before delivering that evidence to the harness", says recording "can apply backpressure", and section 5 says that when storage cannot commit Phoenix will "stop admitting affected calls". Spec section 3 (Capture) says recording runs "all the time and in production, without changing what the agent does". A recorder that withholds a tool result or a model stream segment until a disk commit returns changes timing on every call, and one that stops admitting calls when a disk fills takes the person's production agent down. The design admits the conflict in its own first question to the user, then builds the blocking answer anyway. The cost is not small: SQLite in WAL mode with `synchronous=FULL` syncs the WAL on every commit ([sqlite.org/wal.html](https://sqlite.org/wal.html)), and on macOS a plain `fsync` does not reach the platter unless `PRAGMA fullfsync` is on, which is off by default ([sqlite.org/pragma.html#pragma_fullfsync](https://www.sqlite.org/pragma.html#pragma_fullfsync)). So the promise is either slower than stated or not kept on the platform most people will run it on. A streamed model response has hundreds of segments; one durable commit per segment sits in the token path.

**2. One journal with one writer is a single point of failure, and the design never says how recorders reach it.** MCP stdio proxies and CLI proxies are separate processes that the harness spawns, one per server and one per command invocation. The design gives them "a dedicated writer" on one SQLite database but no transport to it. Either every short-lived CLI proxy opens the database (SQLite allows one writer at a time, so they queue on a lock in the tool-call path) or they talk to a daemon (so a daemon crash stops every tool call, given rule 1). Per-recorder append-only files have neither problem.

**3. SQLite as the authoritative store works against "open formats".** Spec section 2 says traces are "plain, documented, versioned files". Here the plain files are an export "regenerated from committed events", so there are two representations and a converter that can drift. `better-sqlite3` is a native addon, which is a real cost for something "run with npx", and Node's built-in `node:sqlite` is still a release candidate in Node 24 ([Node SQLite docs](https://nodejs.org/docs/latest-v24.x/api/sqlite.html)). The stated reason, "indexed matching", does not need a database: a moment's exchanges fit an in-memory map built when a Replay starts.

**4. An SDK-terminating MCP proxy is not "an ordinary MCP proxy on the wire".** Section 3.1 builds the proxy from "revision-specific transport adapters" using SDK v2 for the current revision and the v1 line for older ones. A proxy that terminates MCP with an SDK server on one side and an SDK client on the other re-serializes every message and answers protocol-level requests itself. That matters now: under 2026-07-28 there is no handshake, clients probe with `server/discover`, and the official v2 client probes a stdio server by spawning a short-lived sibling process and treating an exit as "legacy" ([SDK 2026-07-28 support](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28.html), [versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)). An SDK-built proxy in front of a legacy server would answer that probe as a modern server unless special-cased, which changes what the harness sees. It also lists "server-initiated requests, sessions, resumable streams" as things to record "where a supported revision has" them without saying how two SDK majors in one proxy keep them straight; the current revision removed all three in favor of `InputRequiredResult` and `subscriptions/listen` ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)). A relay that forwards lines and bodies unchanged carries both eras with no era logic at all, and the era logic is needed only in the Replay responder, where it is driven by the recording.

**5. Replay from the mark is left to each recipe and may simply be blocked.** Spec section 3 (Moments) says a Replay "can start from the beginning of the run or from the moment's mark, with everything before the mark frozen exactly as it was". Section 3.5 offers two routes: import "continuation state using a supported harness interface", or run "the original harness through the prefix" and then "start the candidate continuation". The first exists only where a harness offers it. The second never explains how a running process switches from original code to candidate code at the mark. When neither works the mark is "blocked". That makes a core spec feature depend on per-harness work, against "not tied to any one harness". There is a harness-neutral way: launch the candidate from the start and answer every model request and tool call before the mark from the recording, matching model requests by a key that ignores the editable parts of the prompt.

**6. The sandbox stack is heavier than the spec's threat and the clock citation does not support the claim.** The spec's safety rule is that nothing in a Replay can write to a real system, which is a network-and-credentials property. The design adds gVisor "where supported" against kernel exploits by the harness, which the spec never names as a threat, and gVisor's Docker integration is a Linux `runsc install` ([gVisor Docker quick start](https://gvisor.dev/docs/user_guide/quick_start/docker/)) with no supported path on Docker Desktop ([docker/desktop-feedback#364](https://github.com/docker/desktop-feedback/issues/364)). For the clock it cites QEMU's "instruction-count-based virtual time". Instruction counting is a feature of TCG, QEMU's software emulator ([QEMU TCG instruction counting](https://www.qemu.org/docs/master/devel/tcg-icount.html)), so using it means running the harness without hardware acceleration, which is the opposite of fast. It is also unnecessary: a guest kernel owns its own `CLOCK_REALTIME`, so setting the time inside any hardware-accelerated guest before the workload starts gives a guest-wide clock. The design is right that preload injection alone is not enough ([libfaketime](https://github.com/wolfcw/libfaketime), [time_namespaces(7)](https://man7.org/linux/man-pages/man7/time_namespaces.7.html)); I concede that below.

**7. Diverging on every read after an unknown write contradicts the spec's own tiers.** Section 3.6 says "Unknown write semantics invalidate potentially affected recorded reads", ending in a divergence. Spec section 3 says of the simulator "Writes are no-ops", and the fidelity table gives Banking as "Recorded reads, no-op writes". Under the other design's rule a banking Replay diverges on the first read after any write, so that tier cannot run. The honest reading is to keep serving and mark what follows as discounted.

**8. The lock on the success check is weaker than it looks.** The unit table lets the Workbench interface depend on `setup`, the unit that drafts and locks checks. The design says the Improver's capability "does not grant check-approval", but the code that writes checks is linked into the process the Improver drives. Spec section 2 says whoever is trying to pass a check "can never edit it"; that is safer as an import rule than as a permission check.

**9. Formats the spec says "come early" are described but not shown.** Spec section 7 says the plugin interface, manifest and trace specs come early so people can build against them. The other design gives a table of file names and prose for `moment.json` and `check.json`, with no sketch of the expectation syntax the spec enumerates (call with arguments, order, cap, end state, final text, custom TypeScript). It also never says how an agent flags a moment "itself while it runs" (spec section 3, Moments): section 4 says "an agent can mark a Moment immediately" and no unit provides the means.

**10. Additions the spec did not ask for.** mitmproxy as a second interception stack beside Mockttp (a Python dependency for a TypeScript core run with npx). Six provenance values where the spec names four ("real, recorded, derived or synthesized"). A "migration comparison" result type; scenario 4 is a Replay of the set with a different model, which the existing rules already cover. A PTY path, hard-link defenses and hostile-manifest handling are reasonable details, but together with the items above they make a design with sixteen units and three isolation technologies before one moment replays.

**What I take from it.** The revision below adopts these: model credentials stay outside the sandbox and are injected by the gateway; untrusted code (custom checks, emulators) runs in containers with no network, since Node's permission model "does not provide security guarantees in the presence of malicious code" ([Node permissions](https://nodejs.org/docs/latest-v24.x/api/permissions.html)); a guest-wide clock is required where preload fails, and a Replay without a working virtual clock is refused; each Replay runs a frozen candidate built from the base commit plus only the editable diff; samples that cannot be assessed make a comparison incomplete instead of shrinking the denominator; "meets the check" and "improved on baseline" are reported separately; an incomplete list is not evidence of absence; calls made underneath a tool call are linked to it and not counted as agent tool calls; each run carries a coverage record; in-flight calls at a mark are handled explicitly; a pull request is a spec output, not a question; and Ozi gets a recipe.
