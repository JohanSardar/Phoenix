1. **What Capture does when recording is slow or broken.** The other design commits to disk before every dispatch and every delivered segment, and stops traffic when it cannot. I hold only the last bytes of each message until the record is with the operating system, never wait for a flush, and release with a marked gap on failure. My case: SPEC §3 says recording runs in production "without changing what the agent does." A flush per segment paces every streamed response ([SQLite syncs the WAL on each commit at FULL](https://sqlite.org/wal.html)), and halting on a full disk lets Phoenix take down the agent it observes. My rule already gives the property that matters after a process crash (nothing the harness received whole is missing), and the remaining exposure is power loss between flushes. Both designs ask the user; the default should be the one the spec's sentence describes.

2. **Replay from the mark.** The other design requires a continuation import or a hand-off from the original harness, and blocks otherwise. I run the candidate from the start against recorded answers until the mark and stop on drift. My case: the spec requires mark replay as a general capability and gives the harness three declarations, none of them a continuation hook. Re-execution works for any harness that can be launched, including self-built ones. "Frozen exactly as it was" describes the history, which my prefix imposes byte for byte; the prompt is what the Improver is there to change. The continuation mechanisms the named harnesses actually offer are saved transcripts ([Claude Code sessions](https://code.claude.com/docs/en/sessions)), which the other design itself rejects as execution state.

3. **Files or a database as the store.** The other design makes SQLite authoritative, behind one writer in a supervised controller, with JSON Lines regenerated for export. I keep per-recorder append-only files as the only store. My case: SPEC §2 makes the trace an open, plain file, and one representation cannot disagree with itself. Per-process files have no shared writer to be down, need no native addon under `npx`, and can be read mid-run with no index. The one thing the database buys, flush-per-commit durability, is the thing disagreement 1 rejects on the call path.

4. **Discounted pass or inconclusive.** The other design returns inconclusive whenever a required expectation depends on synthesized data. I report the verdict and mark it discounted, never as a plain pass. My case: SPEC §2 says fidelity is reported "so a pass can be trusted or discounted," and §3 says synthesized answers are excluded "where possible." Both sentences presuppose a labeled pass over synthesized data. The other design's dependency-tracking taint has no decidable form; taint by time order does, and it over-taints rather than under-taints.

5. **A repeated read against an unchanged world.** The other design treats a read beyond the recorded count as a miss unless connector code proves reuse safe. I answer it with the last observation, labeled derived, as long as no write has intervened. My case: with no plugin there is no connector code, so the other rule makes the generic recorded tier diverge whenever a candidate looks twice. The world is frozen by definition in a Replay; the last observation of an unwritten world is what a stateful fake would return too, and the label keeps it out of the "recorded" count.

6. **Connector knowledge as data in the core, or only as plugin code.** The other design puts all overlay semantics in plugin code. I keep a small declarative entity map that the core executes. My case: the spec lists the overlay as step 2 of the core chain and builds it before the plugin interface (§10, steps 6 and 8). A data-only map can be written in any language, checked without running anything, and fails closed, because whatever it cannot express is a miss that falls through to an emulator. I narrowed it to lookups by id and simply filtered complete lists for exactly the reason the other design gives: it cannot do recurrence or search, and now does not pretend to.

7. **Crash recovery inside a sample.** The other design commits every resolved call transactionally and requires emulators to publish state transactionally. I keep every attempt and resume an interrupted sample by using its own trace as a frozen prefix. My case: the existing emulators do not offer transactional state, nothing real was touched, and the prefix mechanism already exists, so resume costs no new machinery and reuses the model responses already paid for.

8. **Git for the workspace.** The other design allows a harness with no repository until a patch is exported. I require one. My case: the spec's output is "a patch or pull request against the harness's own repository," and the manifest "can sit in git next to the harness." One code path gives the base identity, the diff, the ignore rules and the editable-path check; a second path for unversioned trees doubles the place where a change could slip past the editable list.
