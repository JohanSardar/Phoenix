The transport/backend split is useful, and a file-based interchange format is the right boundary. The main problems are not missing abstractions: several concrete rules would lose evidence, replay a different world, or certify an unsupported pass.

1. **Capture deliberately loses the evidence Phoenix exists to preserve.** Sections 3.1–3.3 forward before recording, drop events when queues fill, and acknowledge writes without durable synchronization. This conflicts with SPEC §3 Capture and the requested fail-safe behavior. A later gap marker cannot reconstruct a response already consumed by the harness; a crash may prevent even that marker. Independent segment files are a legitimate storage implementation, but one `write()` per line is not a durability protocol. [SQLite’s documentation](https://sqlite.org/pragma.html#pragma_synchronous) distinguishes completed transactions from power-loss-durable commits. The architecture must explicitly choose between production availability and complete recording during storage failure, rather than claim both.

2. **The frozen prefix is not frozen.** Section 3.6 starts the edited harness from the beginning and ignores its system prompt and tool descriptions when matching prefix requests. Those are precisely the things SPEC §3 Workbench says must match. Different code can also change local files, hidden memory, command arguments, and concurrency before the mark, even when model responses are substituted. Recorded stdout does not recreate a file a command wrote. Universal mark restoration cannot follow from the three-field harness declaration. It needs supported continuation import or reconstruction by the original harness with a genuine continuation boundary; otherwise that mode must be blocked.

3. **Moment construction throws away recordings needed after the mark.** Section 3.4 copies exchanges only up to the mark. A moment at the first action consequently has none of the original action’s response or subsequent observations, undermining SPEC §3 Moments and recorded replay. Keep the relevant run evidence, distinguishing frozen prefix, state valid at the mark, and later recorded exchanges. Later evidence must not be silently backdated into the initial world. Section 4 also unnecessarily restricts Scenarios to replay from the beginning, although the spec gives both origins the same replay behavior.

4. **The recorded matcher invents repeatability.** Returning the last answer forever after recorded occurrences are exhausted is not exact replay. Repeated searches, status checks, writes, and paginated requests can return different results. Removing “volatile” arguments can likewise remove an idempotency key or meaningful timestamp. SPEC §3’s first resolver requires a matching recorded call, not a similar call with an indefinitely reusable answer. [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html) canonicalizes representation; it does not establish semantic equivalence or safe response reuse.

5. **The overlay and emulator can disagree about the same world.** Section 3.5 supplies two writable state mechanisms without specifying how an overlay write reaches the emulator or how a recorded successful write changes either. Entity-path metadata alone cannot reproduce recurrence exceptions, attendee notifications, filters, permissions, or pagination. Google Calendar’s [recurrence documentation](https://developers.google.com/workspace/calendar/api/guides/recurringevents) illustrates why “list/get/update” is insufficient. Each connector needs one state authority and explicit transition semantics. A simulator cache keyed only by call also becomes stale after a write, and sharing that mutable cache across samples compounds the problem.

6. **The advertised sandbox has a documented host-access hole.** Docker explicitly says that containers on an internal network can communicate with its gateway address and appropriately configured host services. Therefore `--internal` does not establish the claim that the engine is the sandbox’s only reachable peer. See [Docker’s internal-network documentation](https://docs.docker.com/reference/cli/docker/network/create/#internal). Enforce destination and port restrictions outside the workload, including host and bridge addresses, IPv6, and local channels. A model-provider hostname allowlist also permits more than inference; the broker must constrain API operations, request fields, redirects, and provider-side tools.

7. **Node permissions do not isolate custom checks.** Section 3.8 executes supplied TypeScript in a child Node process and treats the permission model as its security boundary. Node explicitly states that it does not protect against malicious code: [Node 24 permissions](https://nodejs.org/docs/latest-v24.x/api/permissions.html). Checks need OS-level isolation from the controller, credentials, editable harness, and other results. This matters especially for shared moments containing executable checks.

8. **Reporting host time does not satisfy the virtual-clock requirement.** Section 3.6 permits `clock: host` when interception fails. That is honest reporting, but it still violates SPEC §3’s requirement that “now” match the captured moment for the harness and fakes. A startup probe cannot establish coverage of every subprocess or clock API. [libfaketime](https://github.com/wolfcw/libfaketime) documents static-binary and runtime bypasses; [Linux time namespaces](https://man7.org/linux/man-pages/man7/time_namespaces.7.html) do not virtualize `CLOCK_REALTIME`. Use covered clock adapters or a guest-wide clock boundary, and block unsupported replay modes.

9. **The verdict rules can manufacture a pass.** Section 3.8 allows passing whenever the baseline already passed, contradicting SPEC §3’s requirement that an improvement pass be better than the baseline. It also never resolves how diverged samples affect the denominator. More seriously, it discards tainted expectations when any untainted expectation exists, so an easy preliminary assertion can pass while the actual correction is unassessable. A “discounted” pass when all evidence is invented is not a substitute for the locked check. Preserve binding deterministic failures; require sufficient evidence for every required condition; distinguish check satisfaction, improvement, and incomplete assessment.

10. **Recovery changes the experiment without preserving its identity.** Sections 3.7 and 5 rerun unfinished samples but do not preserve accepted model responses, synthesized answers, committed mutations, or the exact candidate contents used by the interrupted attempt. The baseline cache includes only bundle, tree, and model, omitting relevant generation settings, start mode, resolved plugin version, and clock policy. SPEC §3 requires comparisons on the same model and moment. Recovery needs durable operation identities and immutable inputs, not merely a missing-verdict check.

11. **Privacy handling contradicts its own failure policy.** Section 5 stores malformed traffic raw, while SPEC §3 requires recording-time redaction. Parser failure is not permission to persist credentials. Per-event pattern replacement also does not cover secrets split across stream segments, and redaction counts do not explain which evidence was changed or withheld. Persist a safely redacted representation or an explicit unavailable payload. Re-running redaction during sharing must create new artifact references and a new lock when it changes the approved evidence.

12. **Protocol support is broader than the proposed request handler.** A `handle(Call): Answer` interface and request-scoped SSE are insufficient for older Streamable HTTP’s GET streams, notifications, server requests, cancellation, and resumability. The [2025-11-25 transport specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) expressly includes these. The other design is correct about the 2026 stateless revision, and its single-SDK direction is preferable: [the v2 SDK supports both eras with explicit configuration](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28.html). Preserve transport lifecycle separately from normalized tool calls; a second SDK line is not inherently necessary.

13. **Completeness and fidelity are overstated.** A plugin’s declared tier does not establish that its captured state is complete, and a read-only sidecar does not guarantee a consistent full snapshot “before anything goes wrong.” Extra reads may observe later state or only part of a collection. PATH shims miss absolute executable paths and built-ins; model recording proves only what reached the model. SPEC §2 requires honest fidelity. Track coverage, observation time, completeness, and provenance rather than upgrading a connector merely because a plugin exists. MCP itself warns that [tool annotations are untrusted](https://modelcontextprotocol.io/specification/2026-07-28/server/tools).

14. **Some added commitments are unnecessary, while dependencies are missing.** Perpetual support for every older format major, mandatory git worktrees, and an entity-map language are not required by SPEC §§2–3. The build order claims a faithful loop before virtual time exists and calls the clock, emulator, and simulator independent despite their shared state and provenance requirements. It also omits the named Ozi recipe from its recipe inventory. Keep portable schemas, optional plugins, and thin interfaces, but make the build order follow actual capabilities rather than assuming them.
